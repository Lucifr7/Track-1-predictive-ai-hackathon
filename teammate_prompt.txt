1. THE HACKATHON (Track 1: Predictive Model Track)

Theme: "Predict early, decide better." How can AI spot problems before
they become expensive, and help someone decide what to do about them?

Every solution must show four abilities:
- Detect:     predict failures or spot unusual patterns.
- Categorize: say what TYPE of issue it is, not only that something is wrong.
- Prioritize: rank findings by business impact, cost, risk or urgency.
- Explain:    give clear reasoning a non-expert can act on.

A strong solution should:
- solve a specific, real-world problem
- clearly identify the user who benefits
- support decision-making, not just prediction
- cope with noisy or unfamiliar data
- minimise false alarms
- clearly communicate recommendations and reasoning
- demonstrate measurable impact through realistic assumptions

Core judging question:
"Does your model help someone make a better decision, and can you prove it?"

Advice from the organisers:

2. OUR IDEA

A "morning work-order list" for a factory maintenance technician.
The technician has many machines and not enough time to check them all.
Our tool looks at each machine's readings and gives a short ranked list:
which machines to check first, what is likely wrong with each one, why
we think so, and what it costs to ignore it.

It is a ranked to-do list with reasons, not a dashboard.


3. THE DATA

Dataset: AI4I 2020 Predictive Maintenance Dataset (free, from the UCI
Machine Learning Repository). File: ai4i2020.csv, 10,000 rows.

Important: the data is SYNTHETIC. It was generated to imitate real
factory data; it was not recorded from a real machine. We should say
this honestly in the pitch. We believe it models a milling machine (a
machine that spins a cutting tool to shape metal parts), but check the
dataset description on the UCI page before putting that on a slide.

Each row is one machine run. For the demo we treat rows as different
machines in a factory. That is our assumption, not a fact of the data.

Readings (what the model looks at):
- Type: product quality grade, L (low), M (medium) or H (high)
- Air temperature [K]
- Process temperature [K]
- Rotational speed [rpm]
- Torque [Nm]
- Tool wear [min]: how long the current cutting tool has been used

Answers (what we predict):
- Machine failure: 0 = ran fine, 1 = failed
- Five failure-type columns, each 0 or 1:
  TWF = Tool wear failure: the cutting tool wore out. In the data this
        happens when tool wear is around 200 to 250 minutes.
  HDF = Heat dissipation failure: the machine could not cool down.
        Rule: process temperature minus air temperature is below 8.6 K
        AND rotational speed is below 1380 rpm.
  PWF = Power failure: too little or too much power.
        Rule: power (torque x rotational speed in rad/s) is below
        3500 W or above 9000 W.
  OSF = Overstrain failure: a worn tool pushed too hard.
        Rule: tool wear x torque is above 11,000 (type L), 12,000
        (type M) or 13,000 (type H).
  RNF = Random failure: bad luck, no cause in the readings. We ignore it.


4. WHAT WE HAVE FOUND SO FAR

- 339 of 10,000 rows are failures (3.39%). Failures are rare.
- Because failures are rare, accuracy is a misleading score: a model
  that always says "no failure" is right 96.61% of the time and catches
  nothing. We will judge the model with:
    Recall:    of the real failures, how many did we catch?
    Precision: of the alarms we raised, how many were real?
               (low precision = many false alarms)
- Failure counts by type: heat 115, overstrain 98, power 95,
  tool wear 46, random 19.
- Failure rate by product type: L 3.92%, M 2.77%, H 2.09%.
- 24 failures have two or three causes at once, so the tool should be
  able to name more than one problem for a machine.
- 9 failures have no cause recorded, and 18 "random failure" rows are
  not marked as failures at all. We treat these as quirks of the dataset.
